# Acceptance Criteria to Test Inventory

**Requirements baseline:** `word_association_game_requirements.md` v2.6  
**Status:** 67 AC contract oracles are authored and validated against conforming/violating scripted mock traces; application behavior has not yet been tested

This inventory decomposes the 45 active acceptance criteria into 67 case-specific test oracles. Six retired IDs remain reserved: AC-34, AC-35, AC-36, AC-40, AC-48, and AC-49 are technical-requirement checks, not acceptance criteria. Requirements v2.6 fixes expected results for all active ACs. The executable oracle suite accepts compliant scripted mock observations and rejects mutated violations; it validates assertion sensitivity, not product conformance. The same oracle assertions must run against the real application as each increment is implemented. Phase 0 was approved on 26 October 2026. Database/provider checks are separate TR evidence, and deployment checks are not AC-bound or substitutes for AC coverage.

## Mock-oracle validation status

`tests/ac-contracts/oracle-scenarios.ts` records one contract observation for each of the 67 planned AC test IDs. `oracle-validation.test.ts` exercises every oracle twice: a conforming scripted trace must be accepted, and a mutated violating trace must be rejected. These tests establish that the assertion oracles are sensitive to a contract violation before production code exists. They do not establish that Wordpairs currently behaves correctly. Keep application conformance status separate and rerun the same oracles against the real system as implementations are added.

## Implementation evidence

For every mock-gate contract test ID, record its test file/name, mock-validation command and result before the first implementation commit, then record production commit and full-suite regression result. For every post-implementation integration evidence ID, record its actual database/provider/browser command and result when the required system exists; deployment/account checks are recorded against TRs only. These IDs are not represented as mock proof. A fake may validate the application contract at its port but must not be cited as proof that the underlying database serializes concurrent writes or commits an outbox atomically.
