# Reaction test failure analysis

This record distinguishes observed results from explanations that remain unproven. The historical error-context files named in the logs were not preserved; the test-results directory was subsequently reused. They cannot be reconstructed. The original logs and JUnit reports remain alongside their receipts.

The full `round4-candidate` browser run failed the pre-boundary `toBeDisabled` assertion: the control was enabled when the test expected it to be disabled. The test installed a running browser clock, advanced fixture server time by 1,999 ms, and fast-forwarded each page. The original cause is unproven. A running clock and independent server-time advance are plausible contributors, but the retained log does not establish either as the cause. Three later repetitions of the unchanged case passed; they do not explain the earlier failure.

The four subsequent experiment logs each show three repetitions on the local browser and fixture server. The command used is recorded in the session as `npm exec playwright -- test tests/browser/reactions.phase5.spec.ts --config=playwright.pwa.config.ts --repeat-each=3 --reporter=line,junit` on [PRIVATE HOST], but the individual experiment receipts did not record that command or host. Their receipts preserve spec hashes, local end timestamps, revision labels, and exit codes. These earlier runs did not generate unique run IDs or independently record their start times; neither can be reconstructed. The revision labels identify the then-current Git HEAD, not the uncommitted test bytes, which are identified by the recorded hashes and log excerpts.

- `reaction-round5-clock`: install and pause the same initial time, then use `fastForward`. Three of three runs failed because the control remained disabled at the later assertion. Inference: jumping the paused clock can skip intermediate interval callbacks; this log alone does not prove the mechanism.
- `reaction-round5-clock-v2`: use `runFor` but advance the server fixture by 1,999 ms before browser timers. Three of three runs failed because the control was enabled before the expected boundary. Inference: a refresh could observe the fixture's advanced server time while browser time was still advancing; the retained log does not prove the sequence.
- `reaction-round5-clock-v3`: advance the server and paused browser clocks in steps. Two runs passed; one failed at `clock.pauseAt` with `Cannot fast-forward to the past`. Inference: time elapsed between installing and pausing the clock at the same timestamp. The exact v3 spec bytes were not retained, only their hash and the logged stack.
- `reaction-round5-clock-v4`: install one minute before the target, pause at the target, and advance server and browser clocks in steps. All three runs passed. The identical spec hash appears in `reaction-round5-repeat25`, where 25 runs passed, and in the subsequent full source-pinned suite. These results do not establish the cause of the original failure.

The browser observes the cooldown through a 250 ms display timer. The component test in `tests/web/social-panel.test.ts` independently checks the control with supplied values at 1,999 ms and 2,000 ms. Neither local fixture proves hosted delivery or physical-device behavior.
